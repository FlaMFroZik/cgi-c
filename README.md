# cgi-c

Небольшая многопоточная библиотека FastCGI-приложения на C.
Ваш `main.c` + библиотека — это FastCGI-приложение, с которым
работает любой веб-сервер (nginx, Apache, lighttpd, Caddy):
если вы написали баг в своём приложении — это ваша проблема,
библиотека следит только за протоколом (и, честно говоря,
старается)

```
           программа = ваш main.c + libfcgi-server.a (компоновка при сборке)
веб-сервер ──▶ fcgi.c ──▶ thread.c ──▶ fcgi_main()
   ▲        записи      поток        вызов по          │
   │        FastCGI    из пула      указателю         │
   └──────── ответ в записях STDOUT/STDERR ────────────┘
```

## Возможности

- Приложение — **библиотека для вашего `main.c`**, а не
  отдельная программа: код компонуется с вашей функцией на
  этапе сборки (статическая библиотека `libfcgi-server.a`).
  Никаких `.so` и `dlopen()` во время работы.
- Функция подключается при компиляции: `main()` отдаёт её
  адрес в `fcgi_run()` → указатель на функцию типа
  `fcgi_function_t`. Типы проверяет компилятор.
- Два модуля библиотеки: `fcgi` (приложение целиком) и
  `thread` (пул потоков).
- Пул рабочих потоков с очередью соединений; если очередь
  переполнена — соединение закрывается (веб-сервер увидит
  ошибку и ответит клиенту сам).
- Полный протокол FastCGI (версия 1): BEGIN_REQUEST,
  PARAMS, STDIN, ABORT_REQUEST, GET_VALUES, UNKNOWN_TYPE;
  ответ — записи STDOUT, STDERR и END_REQUEST.
- Тело запроса передаётся «голым», байт в байт, с точным
  размером — подходят и двоичные данные с нулевыми байтами.
  Обработчик всегда получает не `NULL`, а строку, завершённую
  `'\0'`, даже если тела нет.
- Пустых ответов не бывает: если обработчик не написал ни байта,
  библиотека сама отвечает `Status: 500 Internal Server Error`
  (веб-сервер счёл бы пустой STDOUT ошибкой протокола).
- Роль RESPONDER; мультиплексирование не поддерживается —
  приложение честно отвечает `FCGI_CANT_MPX_CONN`.
- keep-alive (`FCGI_KEEP_CONN`): несколько запросов подряд
  в одном соединении.
- TCP (IPv4 и IPv6) и Unix-сокет для прослушивания.
- Защита от зависших веб-серверов: общий срок на запрос,
  таймауты сокета, лимит размера тела и переменных.
- Мягкая остановка по Ctrl+C: текущие запросы дорабатывают,
  затем приложение выходит.
- Пример приложения с отладочным режимом без сети:
  окружение — строки `NAME=VALUE` из stdin, ответ — на stdout.
- Самопроверка без веб-сервера: `make test` (25 проверок
  протокола и ответов, в том числе на пустой ответ, keep-alive
  и запросы без завершающей записи STDIN).
- Только POSIX и стандартная библиотека C; сборка — `make`.

## Сборка и запуск

Нужны компилятор C (gcc или clang), `make` и POSIX-система
(а для лучшей работы советую Unix-подобную). Проверено на
Linux (Debian 12, GCC 12, glibc 2.36). Код написан на POSIX,
поэтому должен собираться и на macOS / *BSD, но там не
проверялся.

```sh
make          # собрать библиотеку и пример
make run      # собрать и запустить: ./example/fcgi-server -p 9000 -r example
```

### Тест без веб-сервера

FastCGI нельзя проверить через `curl` напрямую — нужен
веб-сервер или клиент протокола. Для второго случая есть
`example/fcgi-client.py`:

```sh
python3 example/fcgi-client.py 'GET /'
python3 example/fcgi-client.py 'POST /echo' --data 'hello'
python3 example/fcgi-client.py -s /tmp/app.sock 'GET /?x=1'
python3 example/fcgi-client.py 'GET /a' 'GET /b' --keep
```

Скрипт печатает тело ответа (STDOUT), а статус
END_REQUEST — в stderr.

Полная самопроверка (запускает серверы сама, нужен Python 3):

```sh
make test
```

Она проверяет не только пример, но и саму библиотеку: что ни один
запрос не остаётся без ответа, что `Content-Length` совпадает с
телом, что `data` — завершённая `'\0'` строка, что keep-alive и
`fcgi_printf()` работают как обещано.

### С веб-сервером

nginx:

```nginx
server {
    listen 80;
    location / {
        fastcgi_pass 127.0.0.1:9000;   # или unix:/tmp/app.sock;
        include fastcgi_params;
    }
}
```

Apache (mod_fastcgi):

```apache
FastCGIExternalServer /app -host 127.0.0.1:9000
ScriptAlias / /app
```

lighttpd:

```lighttpd
fastcgi.server = ("/" => ("" => ("host" => "127.0.0.1", "port" => 9000)))
```

| Команда        | Что делает                                                        |
|----------------|-------------------------------------------------------------------|
| `make`         | собрать всё: `libfcgi-server.a` и `example/fcgi-server`           |
| `make server`  | только библиотеку приложения                                      |
| `make example` | только пример                                                     |
| `make run`     | собрать и запустить с примером; `make run PORT=9000 ROOT=/var/www`|
| `make test`    | собрать и прогнать самопроверку `tests/test_fcgi.py`              |
| `make clean`   | удалить всё собранное                                             |

Отладочная сборка с AddressSanitizer:

```sh
make clean
make CFLAGS="-O0 -g -fsanitize=address,undefined" LDFLAGS="-fsanitize=address,undefined"
```

### Ключи приложения

Ключи разбирает `fcgi_run()` — передайте ей свои `argc`/`argv`
как есть:

```
./example/fcgi-server [-p PORT] [-a ADDR] [-s PATH] [-r ROOT] [-t N] [-m BYTES] [-T SEC] [-q] [-h]
```

| Ключ       | По умолчанию       | Значение |
|------------|--------------------|----------|
| `-p PORT`  | `9000`             | TCP-порт |
| `-a ADDR`  | `127.0.0.1`        | адрес для прослушивания: `0.0.0.0` — все интерфейсы, `::` — IPv6 и IPv4 сразу |
| `-s PATH`  |                    | Unix-сокет вместо TCP (если задан, `-a` и `-p` игнорируются); файл сокета удаляется при остановке |
| `-r ROOT`  | `.`                | корневая папка. Приложение превращает её в абсолютный путь (не длиннее 255 символов) и передаёт функции как `root` |
| `-t N`     | `16`               | число рабочих потоков (1–1024) |
| `-m BYTES` | `1048576`          | максимальный размер тела запроса и переменных PARAMS (от 1024 байт до 1 ГиБ) |
| `-T SEC`   | `10`               | таймаут: за сколько секунд веб-сервер должен прислать запрос целиком; он же — таймаут чтения и записи сокета (1–3600) |
| `-q`       |                    | не печатать журнал запросов |
| `-h`       |                    | справка |

Например:

```sh
./example/fcgi-server                              # всё по умолчанию
./example/fcgi-server -s /var/run/myapp.sock       # только Unix-сокет
./example/fcgi-server -a 0.0.0.0 -t 4 -T 5 -q      # все интерфейсы, 4 потока, без журнала
```

Код в журнале — то, что вернула ваша функция (или код
ошибки, которую библиотека отправила сама).

**Остановка.** По Ctrl+C (или `kill`) приложение перестаёт
принимать соединения, дожидается текущих запросов и
выходит. Повторный Ctrl+C — выход немедленно.

## Функция-обработчик

Тип функции и точка входа библиотеки объявлены в `fcgi.h`:

```c
#define FCGI_ROOT_SIZE 256  /* размер буфера root, включая '\0' */

typedef int (*fcgi_function_t)(char *root, fcgi_env_t *env,
                                 char *data, size_t size,
                                 fcgi_stream_t *out);

int fcgi_run(fcgi_function_t app, int argc, char **argv);
```

Значит, ваша функция должна выглядеть так:

```c
int cgi_main(char *root, fcgi_env_t *env, char *data,
               size_t size, fcgi_stream_t *out);
```

Имя функции может быть любым: приложение находит её не по
имени (как `dlsym()`), а по указателю, который вы передаёте в
`fcgi_run()`.

### Аргументы

| Аргумент | Тип      | Что в нём |
|----------|----------|-----------|
| `root`   | `char *` | **Корневая папка — буфер ровно на 256 символов** (`FCGI_ROOT_SIZE`, то есть `char[256]`). В нём абсолютный путь к папке из ключа `-r`, например `/var/www` (без `/` в конце). Строка всегда заканчивается `'\0'`, поэтому сам путь не длиннее 255 символов. У каждого запроса своя копия буфера: её можно менять, другим потокам это не помешает. |
| `env`    | `fcgi_env_t *` | **Окружение запроса** — переменные из записей PARAMS, то есть то, что обычный CGI получает в переменных окружения: `REQUEST_METHOD`, `REQUEST_URI`, `QUERY_STRING`, `CONTENT_TYPE`, `CONTENT_LENGTH`, `REMOTE_ADDR`, `SERVER_PROTOCOL`, `HTTP_USER_AGENT` и т. п. Смотреть: `fcgi_env_get(env, "REQUEST_URI")` (вернёт `NULL`, если переменной нет). Карта живёт только во время вызова. |
| `data`   | `char *` | **Тело запроса** — байты из записей STDIN, ровно так, как пришли. После последнего байта дописан `'\0'`, так что текстовое тело можно обрабатывать как строку. Если тела нет, это не `NULL`, а указатель на пустую строку. Буфер можно менять (например, разбирать «на месте»), но нельзя освобождать и хранить после возврата. |
| `size`   | `size_t` | Сколько байт в `data` (без дописанного `'\0'`). Нужен, потому что в теле могут быть нулевые байты (файлы, двоичные данные), а `strlen()` остановится на первом из них. |
| `out`    | `fcgi_stream_t *` | **Поток ответа**. В него пишется полный ответ — строка `Status:`, заголовки, пустая строка и тело (`fcgi_write()`, `fcgi_printf()`...). Библиотека сама разрежет его на записи STDOUT. Закрывать ничего не нужно. |

### Окружение (fcgi_env_t)

```c
fcgi_env_t *fcgi_env_create(void);                    /* пустая карта */
int        fcgi_env_add(fcgi_env_t *, const char *name, const char *value);
const char *fcgi_env_get(const fcgi_env_t *, const char *name);  /* или NULL */
void       fcgi_env_free(fcgi_env_t *);
```

Имена переменных FastCGI чувствительны к регистру и
обычно пишутся заглавными (`REQUEST_URI`, не
`request_uri`).

### Поток ответа (fcgi_stream_t)

```c
int      fcgi_write(fcgi_stream_t *, const char *buf, size_t len);
int      fcgi_write_err(fcgi_stream_t *, const char *buf, size_t len);
int      fcgi_printf(fcgi_stream_t *, const char *fmt, ...);
size_t   fcgi_stream_bytes(const fcgi_stream_t *);
```

`fcgi_write()` — в STDOUT (ответ), `fcgi_write_err()` — в
STDERR (журнал ошибок веб-сервера). Обе возвращают 0 или -1,
если веб-сервер закрыл соединение. `fcgi_stream_bytes()`
показывает, сколько байт уже отправлено в STDOUT.

### Что писать в ответ

Приложение FastCGI само формирует ответ, включая заголовки —
веб-сервер только разбирает то, что вы написали:

```c
fcgi_printf(out,
    "Status: 200 OK\r\n"
    "Content-Type: text/html; charset=utf-8\r\n"
    "Content-Length: 13\r\n"
    "\r\n"
    "<h1>Hi!</h1>\n");
```

- `Status: КОД ОПИСАНИЕ` — код HTTP-ответа (без него
  веб-сервер поставит 200).
- `Location: /куда` — перенаправление (например, `Status:
  301 Moved Permanently` + `Location:`).
- Обычные заголовки (`Content-Type`, `Set-Cookie`, ...)
  проходят в ответ клиента как есть.

### Возвращаемое значение

| Значение          | Что значит |
|-------------------|------------|
| `200`, `404`, ... | код состояния приложения — попадает в запись END_REQUEST и в журнал; обычно это код HTTP-ответа |
| `0`               | ответ отправлен, код не важен (в журнале будет `-`) |
| меньше нуля       | ответ **не** отправлен. Если в `out` ещё не записано ни байта, библиотека сама пошлёт `Status: 500 Internal Server Error` |

Пустой ответ недопустим: если к возврату из функции в `out` не
записано ни одного байта, библиотека **сама** отправит
`Status: 500 Internal Server Error`, какое бы значение ни
вернула функция. Поэтому нельзя «ничего не делать» для каких-то
веток запроса — на каждый запрос должен быть сформирован ответ
(или возвращено отрицательное значение до первой записи).

### Правила для функции-обработчика

Она работает **внутри процесса приложения** (оно с ней
скомпоновано!) и одновременно в нескольких потоках. Поэтому:

1. **Потокобезопасность.** Никаких глобальных переменных без
   мьютекса; `setenv()` не вызывать (она не потокобезопасна —
   для этого и существует `fcgi_env_t`).
2. **Не завершать процесс** (`exit()`, `abort()`) — это
   остановит всё приложение, а не один запрос.
3. **Не хранить** указатели `env`, `data`, `out` после
   возврата — они живут только во время вызова.
4. **Писать ответ полностью** до возврата: библиотека отправит
   END_REQUEST сразу после возврата функции.

## Как написать своё приложение

**1.** Напишите `main.c`: функция-обработчик и `main()`:

```c
#include "fcgi.h"

int cgi_main(char *root, fcgi_env_t *env, char *data,
               size_t size, fcgi_stream_t *out)
{
    const char *uri = fcgi_env_get(env, "REQUEST_URI");

    fcgi_printf(out,
                "Status: 200 OK\r\n"
                "Content-Type: text/plain; charset=utf-8\r\n"
                "\r\n"
                "Привет! URI: %s, тело: %zu байт\n",
                uri ? uri : "-", size);
    return 200;
}

int main(int argc, char **argv)
{
    return fcgi_run(cgi_main, argc, argv);
}
```

**2.** Соберите — можно через библиотеку, можно и без архива,
просто добавив исходники:

```sh
make server                                # -> libfcgi-server.a
cc -o myapp mymain.c libfcgi-server.a -pthread
# или так:
gcc -Wall -Wextra -I /путь/к/cgi-c -o myapp mymain.c \
    /путь/к/cgi-c/fcgi.c /путь/к/cgi-c/thread.c -pthread
```

Компилятор сам проверит, что ваша функция в точности совпадает
с типом `fcgi_function_t` — ошибка всплывёт при сборке, а не
посреди запроса.

**3.** Подключите веб-сервер (см. [сборку и запуск](#сборка-и-запуск))
или проверьте скриптом:

```sh
python3 example/fcgi-client.py 'GET /hello'
```

## Пример: example/main.c

В одном файле лежат **функция `cgi_main()` и `main()`**.
Makefile собирает из него программу `example/fcgi-server`:

```sh
cc -c -o fcgi.o fcgi.c
cc -c -o thread.o thread.c
ar rcs libfcgi-server.a fcgi.o thread.o
cc -o example/fcgi-server example/main.c libfcgi-server.a -pthread
```

`main()` примера короткий. Обычный запуск — передать указатель
на функцию приложению:

```c
int main(int argc, char **argv)
{
    if (argc > 1 && strcmp(argv[1], "-") == 0) /* режим без сети */
        ...;
    return fcgi_run(cgi_main, fargc, filtered);
}
```

А если первый аргумент — `-`, программа делает то же, что
приложение для одного запроса, но без сети: окружение читается
из stdin строками `NAME=VALUE` (пустая строка — конец
окружения), далее идёт тело запроса, ответ пишется в stdout
«голыми» байтами. Так удобно отлаживать логику без веб-сервера
и без протокола:

```sh
printf 'REQUEST_METHOD=GET\nREQUEST_URI=/echo\n\n' | ./example/fcgi-server - .
printf 'REQUEST_METHOD=POST\nREQUEST_URI=/upload\n\nданные' | ./example/fcgi-server - /var/www > page.html
```

Что отвечает пример:

| Запрос      | Ответ |
|-------------|-------|
| `GET /`     | `index.html` из `root`, если он есть, иначе HTML-страница со списком файлов и ссылкой на загрузку |
| `GET /папка/` | `index.html` внутри папки или список файлов; без `/` в конце — 301 на путь с `/` |
| `* /echo`   | тело запроса обратно, как `text/plain`; для пустого тела — короткое пояснение (пустых ответов нет) |
| `GET /путь` | файл из `root` (тип — по расширению) или список файлов, если это папка; `404`, если файла нет |
| `HEAD ...`  | те же заголовки, но без тела |
| `POST /upload` | сохранить загруженный файл в `root/uploads` (multipart/form-data или сырые данные) |
| остальное   | `400`, `403` (выход за пределы `root`, скрытые файлы), `405`, `414` |

На нём видны типичные приёмы: разбор URI и переменных из
окружения, раскодирование `%XX`, построение пути от `root` с
защитой от `..` и символических ссылок, отправка ответа
целиком (`fcgi_write()`), возврат `-1` при нехватке памяти
(тогда библиотека сама пошлёт 500). Функция не использует
глобальных переменных, поэтому безопасна для вызова из
нескольких потоков сразу.

Журнал запросов примера (`-l LOGFILE`) — в формате
Apache/Nginx combined; адрес клиента берётся из `REMOTE_ADDR`
(за FastCGI-запросом стоит веб-сервер, а не браузер).

## Как устроено

### Путь одного запроса

```
  веб-сервер (nginx и т. п.)
    │ TCP или Unix-сокет
    ▼
┌─ главный поток: fcgi.c ─────────────────────────────┐
│ fcgi_run(): poll() + accept() →                     │
│               thread_pool_push(client)                │
└───────────────────────────┬───────────────────────────┘
                            │ очередь сокетов
                            ▼
┌─ рабочий поток: thread.c ─────────────────────────────┐
│ thread_worker() берёт сокет из очереди и вызывает     │
│ pool->task(client, arg)    ← указатель thread_task_t  │
└───────────────────────────┬───────────────────────────┘
                            ▼
┌─ fcgi_connection(): fcgi.c, в том же рабочем потоке ──┐
│ 1. BEGIN_REQUEST → роль, флаг keep-alive              │
│ 2. PARAMS  → fcgi_env_t (окружение запроса)           │
│ 3. STDIN   → data, size (тело запроса)                │
│ 4. server->app(root, env, data, size, &out)           │
│      ↑ указатель на вашу функцию — из fcgi_run()      │
│ 5. STDOUT/STDERR-записи → END_REQUEST → журнал        │
└───────────────────────────┬───────────────────────────┘
                            ▼
          cgi_main() пишет ответ в fcgi_stream_t
```

### fcgi.c / fcgi.h — библиотека приложения

Программы здесь нет: `main()` — у пользователя, библиотека
отдаёт наружу одну точку входа:

```c
int fcgi_run(fcgi_function_t app, int argc, char **argv);
```

Она получает указатель на функцию-обработчик и `argc`/`argv`
от вашего `main()`. Порядок работы:

1. Разбор ключей (`getopt()`).
2. `set_root()` — `realpath()` превращает `-r` в абсолютный
   путь и кладёт его в `char root[256]`.
3. `setup_signals()` — Ctrl+C и `SIGTERM` выставляют флаг
   остановки; `SIGPIPE` игнорируется.
4. `socket_listen()` или `socket_listen_unix()` — слушающий
   сокет.
5. `thread_pool_create()` — запуск рабочих потоков; им
   передаётся указатель на обработчик `fcgi_connection()` и
   указатель на настройки приложения.
6. `accept_loop()` — `poll()` + `accept()`, каждое соединение
   — в очередь пула; если очередь полна, соединение
   закрывается.
7. Остановка: закрыть слушающий сокет →
   `thread_pool_destroy()` (дождаться потоков) → удалить
   файл Unix-сокета (если он был) → вернуть 0.

Из `fcgi.h` доступны и низкоуровневые функции — на случай,
если захочется написать свой цикл вместо готового:

| Функция | Что делает |
|---------|------------|
| `int socket_listen(const char *address, const char *port)` | открывает слушающий TCP-сокет (IPv4 или IPv6) |
| `int socket_listen_unix(const char *path)` | открывает слушающий Unix-сокет (права 0666, старый файл сокета удаляется) |
| `void socket_close(int fd, int linger)` | закрывает соединение аккуратно: `shutdown()` и дочитывание остатков, чтобы ядро не отправило RST и веб-сервер не потерял ответ |

Как библиотека разбирает протокол: читает записи по одной
(заголовок 8 байт + данные + padding), склеивает PARAMS и
STDIN в буферы, а когда приходят завершающие пустые записи —
вызывает вашу функцию. Ответ уходит записями STDOUT сразу,
по мере написания (можно отдавать файлы любого размера, не
держа весь ответ в памяти).

Записи, которые библиотека обрабатывает:

| Запись | Что делает |
|--------|------------|
| `BEGIN_REQUEST` | начинает запрос; роль, кроме RESPONDER, отклоняется (`FCGI_UNKNOWN_ROLE`); флаг `FCGI_KEEP_CONN` разрешает следующий запрос в том же соединении |
| `PARAMS` | копятся в буфер и превращаются в `fcgi_env_t` |
| `STDIN` | копится как тело запроса |
| `ABORT_REQUEST` | запрос отменён веб-сервером — накопленное выбрасывается |
| `GET_VALUES` | отвечает `FCGI_MAX_CONNS`, `FCGI_MAX_REQS` (число потоков) и `FCGI_MPXS_CONNS=0` |
| `DATA` | игнорируется (роль FILTER не поддерживается) |
| неизвестный тип | отвечает записью `UNKNOWN_TYPE` и живёт дальше |

Ошибки и отказы:

| Ситуация | Что происходит |
|----------|----------------|
| Тело или PARAMS больше `-m` | библиотека сама отвечает `Status: 413` / `Status: 431` и закрывает соединение |
| Второй запрос в соединении (мультиплексирование) | `END_REQUEST` с `FCGI_CANT_MPX_CONN`, соединение закрывается |
| Функция ничего не написала (вернула отрицательное или `>= 0`) | библиотека шлёт `Status: 500 Internal Server Error` — пустой ответ не уходит |
| Нет завершающей пустой записи STDIN, но есть `CONTENT_LENGTH` | запрос считается полученным, как только тело набрано целиком; запоздавшая запись игнорируется |
| Нет ни `CONTENT_LENGTH`, ни завершающей записи STDIN | ждём до `-T` секунд, затем закрываем соединение |
| Запрос не пришёл целиком за `-T` секунд | соединение закрывается (HTTP-ошибку выберет веб-сервер) |
| Очередь пула переполнена (256 соединений) | соединение закрывается сразу |

### Связывание на этапе компиляции

`fcgi_function_t` — это тип «указатель на функцию, которая
принимает `(char *, fcgi_env_t *, char *, size_t,
fcgi_stream_t *)` и возвращает `int`». Библиотека хранит
полученный указатель в настройках приложения, и рабочий поток
вызывает функцию обычным вызовом через указатель:

```c
/* main.c:        отдать адрес функции библиотеке                  */
return fcgi_run(cgi_main, argc, argv);          /* cgi_main -> указатель */
/* fcgi_run():  сохранить его в настройках                       */
server.app = app;
/* рабочий поток: вызвать функцию для каждого запроса  */
status = server->app(root, env, data, size, &out);
```

Чем это отличается от динамической библиотеки (`.so` +
`dlopen()`/`dlsym()`):

- **Ошибки видны при сборке.** Тип функции проверяет
  компилятор, а не строка в `dlsym()`: если сигнатура не
  совпала, программа просто не соберётся.
- **Ничего лишнего при работе.** Ни поиска файла `.so`, ни
  разрешения символов: одна программа, один адресный простор,
  обычный вызов функции.
- **Имя функции не важно** — хоть `handle_request`:
  библиотека находит её по указателю.
- **Цена — гибкость**: чтобы заменить обработчик, программу
  нужно пересобрать (с `.so` хватило бы перезапуска с другим
  `-l`).

Тонкость одна, и она та же, что у `.so`: функция выполняется в
процессе приложения, поэтому её падение роняет всё приложение
(см. [правила](#правила-для-функции-обработчика)).

### thread.c / thread.h — пул потоков

Работа разделена между потоками: главный поток только
принимает соединения, а обрабатывают их `N` рабочих потоков
(ключ `-t`). Между ними — очередь (кольцевой буфер сокетов),
защищённая мьютексом, и условная переменная, на которой
свободные потоки ждут работу.

| Функция | Что делает |
|---------|------------|
| `thread_pool_t *thread_pool_create(size_t threads, size_t queue_size, thread_task_t task, void *arg)` | запускает потоки; каждый будет вызывать `task(client, arg)` для очередного соединения |
| `int thread_pool_push(thread_pool_t *pool, int client)` | кладёт сокет в очередь; `-1`, если очередь полна (или пул останавливается) — тогда сокет остаётся у вызывающего |
| `void thread_pool_destroy(thread_pool_t *pool)` | останавливает пул: потоки дообслуживают очередь и завершаются |

Обработчик тоже передаётся указателем на функцию:

```c
typedef void (*thread_task_t)(int client, void *arg);
```

Пул ничего не знает о FastCGI — он просто вызывает
`pool->task(client, pool->arg)`. В приложении это
`fcgi_connection()` из `fcgi.c`, а `arg` — указатель на
настройки (root, указатель на вашу функцию, лимиты).

Сигналы `SIGINT` и `SIGTERM` в рабочих потоках заблокированы,
поэтому Ctrl+C всегда получает главный поток: он сразу выходит
из `poll()` и начинает остановку.

## Отличия от обычного CGI

- **HTTP здесь нет.** Прослушивает не браузер, а веб-сервер;
  HTTP разбирает он, а вам приходят готовые переменные
  (PARAMS) и тело (STDIN).
- **Один процесс — много запросов.** В классическом CGI на
  каждый запрос создавался процесс; FastCGI держит соединение
  и обрабатывает запросы в потоках, поэтому функция-обработчик
  вызывается снова и снова (и должна быть потокобезопасной).
- **Ответ — тоже записи.** Вы пишете заголовки и тело в
  `fcgi_stream_t`, библиотека режет их на записи STDOUT.
- **Появились служебные записи**: GET_VALUES,
  UNKNOWN_TYPE, ABORT_REQUEST, END_REQUEST.

## Ограничения

- Только роль RESPONDER; AUTHORIZER и FILTER отклоняются
  (`FCGI_UNKNOWN_ROLE`).
- Нет мультиплексирования: один запрос в соединении в каждый
  момент (второй параллельный BEGIN получит
  `FCGI_CANT_MPX_CONN`). keep-alive (`FCGI_KEEP_CONN`)
  поддерживается.
- Тело запроса целиком хранится в памяти (до `-m` байт на
  каждый поток).
- Чтобы заменить обработчик, программу нужно пересобрать.
- HTTPS — задача веб-сервера перед приложением.
